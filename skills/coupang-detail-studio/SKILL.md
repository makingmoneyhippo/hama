# Coupang detail studio

Create a complete product detail page as one scrollable, rendered HTML preview, not just a concept, prompts, or disconnected image panels. **Plan 20 exported detail-page panels by default.** Keep ordered exports and motion files for later platform use. The user may provide only a 1688 URL, a few product images, a long reference URL, or any combination. A URL alone is sufficient to start source inspection: do not make the user download product photos as the default intake step. Treat the product and reference as different sources: the product supplies identity and facts; the reference supplies transferable storytelling, pacing, and visual methods.

## 0. Confirm coverage and essential sale facts before production

In the **first assistant reply for every new product detail-page job**, ask the user conversationally, without a table: **“상세페이지는 기본 20장으로 만들게요. 그중 움직이는 WebP는 몇 장 넣을까요? 예: 10장.”** If the user has not supplied a product link or photos, ask for those in the same short reply. Ask for a number of panels only; do not offer a percentage or ratio in the question. Ask even when the user supplied only a product link or images; do not defer the question until after source inspection or planning. If the user already specified a target for **this product** in the request or current conversation, record it and do not ask again. A target chosen for a previous product is not a standing default unless the user explicitly made it one. If the user volunteers a percentage, `N out of T`, or “all”, convert it to a count and confirm the count in the work plan; if the user says “알아서”, recommend a count based on the product's use and the reference. Do not silently pick a quota or treat an example number as the user's answer. Continue read-only source inspection while waiting, but do not finalize animation allocation or start page/media production until the answer arrives.

Count **exported detail-page panels** as the total `T`, normally 20; each numbered HTML section/export is one panel even if it contains two photos. Exclude gallery thumbnails, icons, backgrounds, repeated copies of one animation, and still fallbacks. Count each distinct, reviewed, actually animated WebP used in a primary panel once. For a percentage `P`, set the target to `ceil(T × P / 100)`; for example, 70% of 20 panels means 14 animated WebPs. An exact count stays exact. `17 out of 20` sets both the 20-panel total and 17 animated slots unless the user revises them. If the page plan changes, recalculate a percentage target or preserve the exact count and tell the user about any conflict. Record target `N/T`, the planned animated panel IDs, and the delivered `N/T` in the brief and final handoff. Never lower the requested number without the user's direction; if trustworthy motion cannot be made for a slot, report the shortfall clearly.

After inspecting the supplied listing/images, confirm **brand, final product name, material, every sold color/option, and actual size/dimensions for each option** before making the buyer-facing page. Reuse facts already confirmed in this conversation or evidenced by the selected SKU; do not ask twice. Ask for all missing facts in one short question before image, animation, or HTML production. Offer the values found in source materials for correction when they are merely seller claims. If the user cannot supply an essential value, continue source investigation and storyboard planning, but pause buyer-facing page production rather than filling the final panel with guesses or calling a placeholder page complete.

## 1. Establish evidence

- **Link-first intake comes before creative production.** When given a 1688 URL, take the initiative to open it through the current authorized computer-use browser and inspect the live page as a user would. Reuse an existing signed-in session when available; navigate the listing, switch product options, open galleries, scroll the full detail section, and inspect embedded GIF/video over time. Collect the representative product images and relevant media into a private source-reference folder when the browser permits saving them. Record each source URL or browser location and distinguish the selected listing from recommendations or other SKUs. Do not ask the user to download photos merely because a link was supplied.
- **Handle sign-in in the same session.** Navigate to the site's ordinary sign-in flow and use an existing session or browser-managed login when it works. If password entry, passkey, QR scan, OTP, CAPTCHA, account consent, or security verification requires the account holder, hand that exact browser step to the user, say what to do and where, then resume inspection in the same authenticated tab after the user finishes. Do not ask for passwords, one-time codes, cookies, or session tokens in chat, and do not claim an account is logged in until the product page is visibly accessible.
- **Respect access boundaries.** If the computer-use tool or site security policy rejects the page, stop attempts to access that site; do not switch to another browser, CLI, HTTP client, proxy, or scraping service to work around the rejection. State the specific blocker and ask for the smallest useful user-supplied handoff (for example an authorized page export, option/spec screenshot, or product photos). Continue only with evidence already accessible. Ordinary sign-in and human verification are handoff steps, not a reason to skip the link-first attempt.
- **Finish a source audit before making the page.** Inventory the gallery, every actual sale option, measurements, materials and components as stated, included accessories, seller claims, full detail content, and embedded motion; save stills and sampled time points for GIF/video where permitted. Keep a source-to-claim ledger and flag missing facts. Briefly tell the user what product and options were found, what assets and facts were captured, and which essential items remain unverified. Once the five final-panel facts above are confirmed, proceed to the storyboard and production without a routine approval. Ask only for an essential missing choice or account-holder action; never invent a missing value.
- Treat every 1688/supplier image or video as a **reference for product identity and facts only**. Do not place, crop, recolor, remove text from, or otherwise republish its pixels in any buyer-facing panel, animation, export, or standalone HTML. Generate fresh product studio, detail, and lifestyle imagery from the references; if a product-specific fact cannot be shown faithfully in a generated scene, leave that visual out and keep the fact in the internal evidence ledger. Do not let a reference image accidentally enter the bundled media package.
- If given files, inspect every image. Group shots by actual product and variant before choosing one product to feature. A seller's catalog or unrelated recommendation tiles are not evidence that all pictured items are one SKU.
- For a long reference URL, apply `reference-detail-audit` to the full page, including motion and ending sections, or read its completed audit if already available. Extract structure and techniques rather than copying brand, illustrations, wording, numeric claims, or layout pixel for pixel.
- Maintain a fact ledger: `observed in product image`, `stated by seller`, `independently verified`, `reasonable idea needing evidence`, and `unknown`. Keep the evidence ID or source beside each claim. Ambiguous material, dimensions, load, durability, certification, factory history, or comparison claims stay out of publishable copy until verified. A seller graphic is a claim, not an independent test result.
- Collect every sold option's actual color and dimensions for the single final buyer-facing panel. Separately identify the product-information category and maintain a seller-listing disclosure ledger for any additional fields required by the platform or law. Keep missing disclosure facts visible internally; do not infer origin, age suitability, or dimensions from photos.
- Collect the seller's genuine customer-review sources and the user's brand for this SKU. Use the brand confirmed for the current product, even when an earlier product used another name; do not invent customer experiences, brand history, factories, certifications, or warranty promises. Read [disclosure-and-trust.md](references/disclosure-and-trust.md).

## 2. Plan the persuasion before designing

Build a ranked benefit bank from buyer relevance, demonstrability, evidence confidence, differentiation, and objection resolution. Then write a **buyer-question storyboard** before making visuals. For every proposed screen record: the buyer's current doubt, the one takeaway they should grasp in two seconds, the visual that conveys it, supporting source, copy, motion need, and why the next screen follows. Assign the requested animated WebP slots to distinct moments where movement conveys a useful change; distinguish functional demonstrations from ambient or decorative movement. Reject screens that only restate an adjective or require a paragraph to understand. Read [selling-point-expansion.md](references/selling-point-expansion.md) for varied, evidence-backed expansion.

Use [page-architecture.md](references/page-architecture.md) as the default 20-panel map. Panels 1–19 carry the product story, use scenes, evidence, objections, optional genuine reviews, and a short consistent cue for the SKU's confirmed brand. **Panel 20 is one combined product-information and option/size panel.** If the user explicitly requests another total, place this panel at `T`. Do not stretch a weak feature with repeated copy just to fill 20; find distinct buyer questions, proof, use moments, or compatibility decisions, and mark any unsupported claim as missing evidence.

Transfer the reference's *felt* method: large direct claims, visual proof, changing scene types, escalating reasons to care, and length earned by new information. Do not borrow its product claims or design identity. Sequence may recur from problem to action to payoff, then context, proof, choice, and objection; choose the order that fits the item. A tiny feature may support several scenes if each answers a different buying question. Do not use page length or panel count as a proxy for persuasion.

For an everyday accessory, first stage the familiar moment in which the buyer uses it: where the item is before use, what the hand does, and what the buyer can do after. Show the same benefit from distinct buyer questions (finding, attaching, detaching, carrying, checking fit) only when the screen adds a new action or decision. Prefer a clear situation and payoff over repeated labels about component shape.

Before production, make a one-page art direction: audience, emotional tone, product color and material, restrained palette with each color's role, headline/body size hierarchy, image treatment, and planned light/dark rhythm. Check a few adjacent screens together. If neighboring backgrounds feel arbitrary or compete with the product, revise the palette before producing the whole page.

## 3. Produce image-led scenes and real motion

Create large, visual-first screens. Each screen needs one main idea and a visible product, action, contrast, or useful diagram. Put the decisive Korean line in prominent type; captions support the image. Move dense specifications to dedicated choice aids. At the actual 790px export width, use roughly 48–72px for main claims and 28–36px for supporting copy as a starting point, then inspect a phone-width rendering and adjust. Avoid tiny English eyebrow labels and multi-line prose doing the selling. Reserve small type for genuinely secondary labels, with readable contrast.

Keep the chosen SKU's shape and parts faithful. Use verified source photos to check anatomy and factual claims internally, then produce wholly new buyer-facing studio, detail, and lifestyle images. Compare each generated image with the source and reject part-count, shape, color, mechanism, or option drift. Do not place automatic “AI 생성 이미지”, “AI 연출”, or similar production-method badges on the sales panels. Record generation method, source references, and limitations in the internal media manifest instead. Use natural copy such as “사용 예시” when needed so a staged scene is not presented as a measured test or genuine customer experience. Identify bags, keys, key rings, or other props that are not included with the product. A generated image or video never establishes load capacity, durability, safety, certification, or an unobserved mechanism. Check separately for any legally required disclosure, such as a virtual endorser; do not remove a required notice. Alternate scene types and breathing room; show major benefits through action, close-up, scale, context, and objection handling when evidence allows.

Place a review section in the middle **only when genuine, attributable reviews for the same product/option are available**; quote them faithfully and identify the source and any incentive. If not, use a clearly labeled use scenario, buyer question, or FAQ, never a fabricated customer voice, rating, or testimonial. Include one compact cue for the confirmed brand within panels 1–19. Keep it product-relevant; do not invent a brand biography or change an established brand identity by category. Follow [disclosure-and-trust.md](references/disclosure-and-trust.md).

Make the final panel a single readable product card with **only these buyer-facing information fields: 브랜드, 제품명, 소재, 색상/옵션, 사이즈**. Combine option images and each option's verified measurements in that same panel; show units and category-appropriate size conventions. For S/M/L, show each measured size. Keep the text accessible in HTML. Do not add a second specification page or append origin, manufacturer, age, warranty, or warnings to this designed card. Maintain a separate category-specific disclosure ledger and complete any additional legally or platform-required information in the actual listing workflow; unknown mandatory disclosures block a publish-ready claim. Read [disclosure-and-trust.md](references/disclosure-and-trust.md).

Create a **motion brief before finalizing the storyboard**. Inventory source GIFs/videos frame by frame, including those inside reference URLs. For every planned animated WebP slot, specify the buyer question, actual change to show, source evidence, first/action/last frame, caption, loop, fallback still, and intended Coupang placement. Read [motion-production.md](references/motion-production.md).

Default every animated WebP to **3 seconds at 20 fps with 60 output frames**. For an action that genuinely needs longer, use **4 seconds at 20 fps with 80 output frames**. Record the selected duration per panel; 50 ms per output frame makes the timing exact. These are finished-file requirements, not a license to repeat a few stills: inspect temporal continuity, hand/object contact, product geometry, and the loop seam. If a source sequence cannot produce smooth, truthful motion at this standard, revise the action or acquire better source motion before counting it as delivered.

For **newly made animation**, use the image generation tool available inside Codex (GPT Image, with the current model version when exposed) and local GIF/WebP encoding. If that tool returns a genuine multi-frame GIF, inspect and convert it. If it returns a still PNG, generate a sequential frame sheet, crop the cells, encode a real GIF, and convert it to animated WebP. Never claim a model version that the tool did not expose, and never present a renamed still as motion. Rework failed frames before counting a slot as delivered. Do not use Higgsfield or another paid video generator for this skill unless the user explicitly changes this preference. Only user-owned original footage with clear rights may be edited and converted directly; 1688/supplier footage stays reference-only.

For an ordinary use action supported by source photos (for example a lever visibly open and closed), an AI-rendered sequence may explain the action only if the product, hand contact, and complete physical result survive frame review; record it internally as a recreation, never as proof of measured performance. Do not reuse supplier video frames in the delivered animation. If the source does not establish the mechanism, request footage rather than inventing it. Deterministic motion may animate truthful newly made stills, callouts, or verified diagrams. A camera pan, zoom, or text sweep is decorative and never counts as a use demonstration. Produce and inspect actual encoded motion files, not a static placeholder or renamed extension.

Build the **full-length HTML page first**. It must show the entire sequence in one continuous scroll, with working inline motion, a still fallback, and Korean copy. Keep production provenance in the internal media/claim manifest, not as automatic buyer-facing AI badges. Open the rendered HTML in Codex or the available browser and inspect the top, middle, and ending in context; a folder of separate PNGs is not the finished preview. Check that the combined final panel is readable at phone width. When practical, also bundle a standalone HTML file with its media embedded so the user can open one artifact. If a browser security policy blocks local-file opening, do not route around it through another browser surface; deliver the standalone HTML link and a full-page static preview for the user to open directly. Deliver editable source, that single-page preview, 20 ordered exports by default, motion files, media/claim manifest, and missing-evidence list. Verify that neither source pixels nor source files appear in the buyer-facing outputs or bundle.

For later Coupang upload, distinguish gallery images, detail-editor images, and supported video positions. Check current official guidance; verify the seller account's actual rendered upload only when the user is preparing to publish or explicitly requests that check. GIF/WebP support cannot be inferred from extension alone; keep a still fallback and label untested placements as unverified. Platform placement uncertainty does not prevent completion of an HTML preview, but never call the page upload-verified or publish-ready without that separate check.

## 4. Score, revise, and stop

Use [quality-gate.md](references/quality-gate.md) on the actual rendered HTML page and encoded motion, not merely on the outline. Grade each criterion with a brief evidence-based reason and links to sections or assets. Rework the lowest-scoring high-impact issue, rerender, and rescore the whole page. For each iteration, inspect at phone size and check the complete sequence, not only isolated panels. A missing functional demo, unreadable typography, random color rhythm, text-led screens, or unfulfilled animated WebP target cannot be compensated by a polished hero or a high numerical total. Continue while an HTML-preview hard gate fails or the score is below the threshold. Stop only when the full preview deliverable and the user's motion allocation pass and no required work remains. Do not silently lower the rubric or WebP target to fit the draft.
